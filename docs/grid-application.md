# Journalled native grid application

`layout-apply-grid --spec <grid.json> --expected-project <copy.evo> --group-id <exact-group-id> --evidence-directory <new-directory>` and MCP `apply_grid_layout` connect the existing planner, fixture inspector, guarded movement and geometric comparison.

The command validates target footprints against the supplied room/exclusions, then inspects the existing explicitly counted group. Counts must agree, runtime identities must be unique and native rotations must be zero. Existing fixtures are assigned to target positions in Y/X/Z spatial order. This is an explicit geometric assignment, not a product-identity match or lighting optimization. It creates and deletes no fixtures.

Each movement's intent is recorded before invoking the independent native backend. Successful calls are marked committed. An exception leaves the overall run failed with previous committed steps and the pending step intact, and stops further operations. There is no automatic retry, rollback or resume. A new output directory is required, preserving previous evidence. An atomic file replacement updates only this run's journal.

After all moves, a fresh native group inspection is matched one-to-one against the plan. The journal reaches `verified` only after that comparison passes. This means the supplied realized group's geometry matches; it does not imply whole-project completeness, correct photometry, native persistence or lighting performance. Save/reopen and calculation remain separate steps. Cached results are cleared by movement operations.

Current limits: nonempty zero-rotation grids, equal existing fixture count and a 7200-second operation bound. The native Luminaires parent is expanded for recognized group IDs; other collapsed ancestors may still need explicit `desktop-project-tree` expansion. No creation, deletion, rotation, automatic rollback or resume is provided. Cooperating worker requests are excluded for the entire run by the desktop mutex. Human input and third-party automation remain outside that lock. The synthetic example is `examples/synthetic-apply-grid.json`; no assignment layout is included.

Group inspection is collected across bounded pages with a consistent runtime-identity/order token. The workflow checks continuation advancement and the realized total count before mutation, then collects fresh pages again for final verification. It does not assume the first page is the entire group. The current implementation retains ItemContainer references across every read and edit in one native process, including final readback. Virtualized rows are materialized before selection. Every movement still checks runtime identity and expected prior coordinates. Whole-project inventory and large-scale movement acceptance remain separate.

## Persistent worker revision

The public CLI/MCP now dispatches one `apply-grid` worker, holding the desktop lease from inspection through final verification. Cached results are cleared before retaining the first inventory; a failure can therefore leave results cleared even if no fixture moved. The journal is created before that action. A run's partial movement outcome must be read from its steps, not inferred from the exception alone.

For each guarded movement, the retained raw native element is realized/scrolled into view, then its runtime identity and existing XYZ are rechecked. Final geometry is read again rather than copied from targets. The native Goto command is used when WPF omits the unselected lighting-mode tab from UIA; no hard-coded screen position is used.
